# HomeVlad Cloud · Proxmox Billing

Панель управления и биллинга для Proxmox VE. Текущая бета-версия — v2.5.1-beta8.18 ([каталог обновлений](updates/index.json)).

- Управление узлами и зонами доступности, создание и мониторинг ВМ QEMU и контейнеров LXC.
- Тарифы, квоты, пополнение баланса и автоматические списания.
- Консоль QEMU и LXC из кабинета пользователя и админки через домен панели.
- Полный кабинет и компактный лайт-режим. Переключатель находится в меню аккаунта, светлая и тёмная темы выбираются отдельно.
- Адаптивная вёрстка и PWA. На iPhone откройте панель по HTTPS в Safari и выберите «Поделиться» → «На экран „Домой“».
- Тикеты поддержки, Telegram-боты, пользовательская вики и страница состояния платформы.

## Установка в Docker

Понадобятся Git, Docker с Compose v2, домен с DNS-записью на сервер и доступные входящие порты 80 и 443. Для выпуска сертификата Let's Encrypt порт 80 должен быть свободен на время запуска `init-ssl`.

```sh
git clone --branch main https://github.com/mortal2424/proxmox-billing-pub.git
cd proxmox-billing-pub
cp .env.example .env
chmod 600 .env
mkdir -p webroot uploads logs backups docker/proxmox-tls
```

1. В `.env` укажите `DOMAIN` без схемы и порта, `EMAIL`, имя БД и пользователя. Замените примеры паролей в `DB_PASSWORD` и `MYSQL_ROOT_PASSWORD` уникальными значениями. Добавьте `PROXMOX_NODE_KEY`, как описано в разделе о шифровании.
2. Запустите стек и проверьте журналы.

   ```sh
   docker compose up -d --build
   docker compose ps
   docker compose logs --tail=100 init-ssl apache nginx
   ```

3. Apache автоматически импортирует схему в пустую БД и создаёт `includes/config.php`. Откройте `https://<ваш-домен>/admin/create_admin.php` и создайте первого администратора. Ограничьте доступ к этому маршруту на время первичной настройки и закройте его после создания аккаунта.
4. В админке добавьте узлы Proxmox, настройте тарифы и проверьте доступ к API и запуск консоли. Сбор метрик и списания уже настроены через cron внутри контейнера Apache.

При неудачной выдаче сертификата `init-ssl` создаёт самоподписанный сертификат. Перед публичным запуском убедитесь, что Nginx обслуживает домен с доверенным сертификатом, и проверьте процедуру его продления. Nginx читает сертификаты из тома `ssl-certs`, а Certbot хранит данные продления отдельно. Обновлённые файлы должны попасть в том, после чего Nginx должен перечитать конфигурацию.

### Обновление Docker

Из существующего каталога установки сохраните резервные копии БД, загруженных файлов и конфигурации. Сохраните прежний `PROXMOX_NODE_KEY` и прежнее имя Compose-проекта, чтобы стек использовал тот же том БД.

```sh
git switch main
git pull --ff-only origin main
docker compose up -d --build
docker compose ps
```

Образ Apache собирается из исходников текущего коммита main. Инициализация пропускает импорт для БД с существующими таблицами. Для старой БД, созданной до появления пулов размещения, выполните после сборки `docker compose exec --user www-data apache php cronjobs/create_node_placement_pools.php`. Команда сохраняет существующие пулы и добавляет недостающие элементы схемы. Для сохранения данных не удаляйте том `db_data`.

### Доступ к БД через phpMyAdmin

Если нужен phpMyAdmin, подключите дополнительный файл к основному Compose-проекту и ограничьте порт 8081 локальным интерфейсом, заменив `8081:80` на `127.0.0.1:8081:80` в дополнительном файле.

```sh
docker compose -f docker-compose.yml -f docker-compose.phpmyadmin.yml up -d phpmyadmin
```

Подключайтесь через локальный адрес или SSH-туннель. Сервер БД внутри Compose-сети — `db`.

## Установка без Docker

Рекомендуемая версия PHP — 8.2, как в Docker-образе. Понадобятся HTTPS, MySQL или MariaDB, Composer и расширения PHP из проверки установщика, в том числе PDO MySQL, cURL, OpenSSL, SSH2, mbstring, XML, GD, BCMath и Intl.

1. Разверните исходники в корне сайта. Установите зависимости командой `composer install --no-dev --optimize-autoloader`.
2. Создайте пустую БД и пользователя для неё. Подготовьте каталоги `uploads`, `logs`, `cache`, `temp` и `backups`. Предоставьте PHP права на запись в нужные установщику каталоги, включая `includes` для создания конфигурации.
3. Ограничьте доступ к `/install/` на время установки. Откройте `/install/install.php` и следуйте мастеру, который импортирует `install/sql-install.sql`, создаёт `includes/config.php` и настраивает администратора. При ручной установке импортируйте схему в пустую БД, заполните конфигурацию по `includes/config.php.simple` и создайте первого администратора через `/admin/create_admin.php`.
4. После установки закройте установщик и маршрут создания первого администратора. Проверьте, что веб-сервер закрывает доступ к служебным файлам, логам, резервным копиям, SQL-дампу и вложениям тикетов, а в `uploads` нельзя исполнять PHP. На Apache примените правила `.htaccess`, для Nginx настройте эквивалентные ограничения. Примеры есть в каталоге [docker](docker/).
5. Настройте CLI-задачи и при необходимости прокси консоли.

### Задания cron

Используйте [расписание Docker](docker/crontab.txt) как образец. На обычном сервере замените абсолютные пути и пользователя на подходящие для установки. При добавлении в пользовательский `crontab -e` уберите поле пользователя после расписания.

| Период | Скрипт | Назначение |
| --- | --- | --- |
| Каждый час | `admin/cron_charge.php` | Списания по тарифам. Достаточно одного задания |
| Каждые 5 минут | `admin/update_node_stats.php` | Статистика узлов |
| Каждые 5 минут | `cronjobs/check_node_health.php` | Доступность API гипервизоров |
| Каждую минуту | `cronjobs/backup_cron.php` | Запуск резервных копий по сохранённым расписаниям |
| Каждые 5 минут | `api/collect_lxc_metrics.php`, `api/collect_vm_metrics.php` | Метрики LXC и ВМ, два задания |
| Каждые 2 часа | `api/update_proxmox_tickets.php` | Обновление билетов Proxmox |
| Каждую минуту | `includes/vm_ip_updater.php` | Обновление IP-адресов |
| Ежедневно в 03:00 | `api/clean_old_metrics.php` | Удаление старых метрик |

## Консоль QEMU и LXC

Панель проверяет права на ВМ или контейнер, а прокси устанавливает соединение с Proxmox. Браузеру достаточно HTTPS-сессии панели. Для установки без Docker настройте сервис, статические клиенты и WebSocket по [инструкции прокси](console/README.md).

В Docker прокси и клиенты noVNC и xterm.js входят в образ Apache. Nginx проксирует `/console/socket`, порт 8765 остаётся внутри Docker-сети. Сервер панели или контейнер Apache должен достигать API узла Proxmox, обычно на TCP 8006.

- Для частного CA положите проверенный публичный PEM кластера в `docker/proxmox-tls/pve-root-ca.pem` и укажите в `.env` `PROXMOX_CA_FILE=/etc/proxmox-tls/pve-root-ca.pem`. Имя узла должно присутствовать в сертификате.
- Для отдельного самоподписанного сертификата прокси поддерживает привязку по отпечатку. Укажите `PROXMOX_CERT_PINS=/etc/proxmox-tls/pins.json` и положите в этот каталог JSON вида `{"pve.example.org:8006":"<64 шестнадцатеричных символа SHA-256>"}`. Сверьте отпечаток на узле и обновите его при смене сертификата.
- Переменные выше относятся к прокси консоли. Для PHP-запросов к API с проверкой TLS добавьте CA узла в хранилище доверия PHP/cURL, включая контейнер Apache при установке в Docker.

После смены переменных примените их через `docker compose up -d`. Проверьте запуск консоли работающих QEMU и LXC из кабинета и админки в браузере, где открыта только сессия панели. При сбое проверьте журналы Apache и Nginx, TLS, доступ к API и права учётной записи Proxmox на консоль.

Для PHP-проверки состояния узлов используются те же `PROXMOX_CA_FILE` и `PROXMOX_CERT_PINS`. Без переменных окружения приложение ищет `.proxmox-ca.pem` и `.proxmox-cert-pins.json` на уровень выше веб-корня. Файл отпечатков привязывает SHA-256 сертификата к точной паре адреса узла и порта.

## Шифрование паролей узлов Proxmox

Приложению и CLI-задачам нужен один и тот же ключ из 32 случайных байт в Base64. Сгенерируйте его командой `openssl rand -base64 32`. В Docker задайте ключ в `.env` до первого запуска.
Перед обновлением передайте его через `PROXMOX_NODE_KEY` или положите в файл
`.proxmox-node-key` рядом с каталогом приложения, на уровень выше веб-корня.
Ограничьте чтение файла пользователями PHP и cron. Храните резервную копию ключа отдельно от БД.

Сначала обновите все PHP-обработчики и задачи cron. Убедитесь, что PHP и CLI
используют один и тот же ключ. Затем выполните миграцию от пользователя cron:

```sh
php cronjobs/encrypt_node_passwords.php
```

В Docker запустите `docker compose exec apache php cronjobs/encrypt_node_passwords.php`.

Миграция повторно проверяет уже зашифрованные записи и откатывается при ошибке.
После миграции проверьте доступность API и открытие консоли. Для восстановления
старого кода потребуется совместимая резервная копия базы. Пароли пользователей
по-прежнему проверяются по хешам из `users.password_hash`.

## Зоны доступности и пулы размещения

1. В «Настройки Proxmox» создайте зону, добавьте одну или несколько нод по API-токенам и включите их доступность для пользователей.
2. В действиях каждой ноды откройте «Пулы внешних сетей и хранилищ». Создайте сетевые пулы и отметьте разрешённые мосты или активные SDN VNet. Для каждого пула хранилищ отметьте разрешённые ресурсы. Нода может иметь несколько пулов каждого типа.
3. Укажите понятное название для пользователей. Например, пул с `NVME-SSD1TB` может называться «Быстрый NVMe SSD». Одинаковые коды пулов на разных нодах объединяют их ресурсы в пределах зоны. Код пула используется при размещении, понятное название можно редактировать.
4. В кабинете выберите ВМ или LXC, тариф, зону, сетевой пул либо явно разрешённую SDN и пул хранилищ. Для ВМ выберите cloud-образ или ISO. Для LXC нужен шаблон. Панель проверяет свободную память и объём диска, CPU, доступность сети и образа. Для QEMU хранилище должно поддерживать `images`, для LXC — `rootdir`.

Состав и название пулов меняются в форме редактирования. Удаление после подтверждения убирает пул с выбранной ноды и влияет на новые заказы. Если подходящей ноды нет, проверьте, что хотя бы одна включённая нода зоны поддерживает выбранную комбинацию сети, хранилища и образа.

На обновлённой установке без таблицы пулов выполните один раз `php cronjobs/create_node_placement_pools.php` от пользователя сайта. Свежая установка получает таблицу из основного SQL.

## Установка ВМ из cloud-образов

Каталог «Образы ОС» → «Cloud-образы» включает Ubuntu 22.04, 24.04 и 26.04 LTS, Debian 12 и 13, CentOS Stream 9 и 10 для x86-64. Для CentOS Stream 10 процессор ноды должен поддерживать x86-64-v3. На ноде Proxmox VE 9.2 подготовьте активное файловое хранилище с типом содержимого `Import`. Хранилище исходника может отличаться от пула, в который будут размещаться диски ВМ.

Выберите ноду и раскройте нужный образ. Укажите название для пользователей и активное хранилище `Import`. Кнопка добавления ставит загрузку в очередь или публикует уже размещённый файл. Чтобы поменять хранилище, выберите новый источник и подтвердите выбор. Пока скачивается новая копия, заказы продолжают использовать прежнюю. После успешной проверки контрольной суммы новый источник становится активным. Старая копия остаётся в Proxmox, где её можно удалить отдельно.

«Убрать из каталога» скрывает образ для новых заказов на этой ноде. «Удалить файл» доступно для токена с `Datastore.Allocate` на конкретном хранилище. При физическом удалении из общего хранилища файл исчезает для всех использующих его нод. Диски уже созданных ВМ хранятся отдельно.

Для существующей установки без Docker примените схему `php cronjobs/create_cloud_image_settings.php` от пользователя сайта. На время перехода установите пакет и сразу примените схему перед использованием раздела. Затем добавьте минутное задание в crontab пользователя PHP. Оно должно иметь доступ к тому же ключу шифрования и настройкам TLS, что и сайт.

```cron
* * * * * /usr/bin/php /путь/к/панели/cronjobs/process_cloud_image_imports.php
```

Для Docker пересоберите и пересоздайте контейнер Apache по инструкции обновления Docker. Инициализация применит схему, а Supervisor запустит обработчик импорта от пользователя Apache. Серверу или контейнеру нужен HTTPS-доступ к репозиториям издателей и место для временного файла образа. Для ручной загрузки из терминала остаётся команда `php cronjobs/import_cloud_image.php 1 NFS-DISK debian-12`.

В форме заказа QEMU по умолчанию выбран cloud-образ. После выбора зоны появятся доступные образы. Панель импортирует системный диск в выбранный пул, увеличивает его до размера тарифа и через cloud-init настраивает учётную запись и DHCP. Имя пользователя и минимальный объём диска показаны под выбранным образом. Сеть должна выдавать адрес по DHCP. Для ручной установки можно переключиться на ISO.

### Windows Server 2022 и 2025 с Cloudbase-Init

Панель использует подготовленный администратором самостоятельный QCOW2 x86-64. Для запуска профиля Windows нужна поддержка x86-64-v2 и AES на гипервизоре. Для коммерческих заказов используйте образ и лицензию, которые разрешают развёртывание на вашей инфраструктуре. Оценочные образы используйте в изолированной проверке. [Microsoft Evaluation Center](https://www.microsoft.com/en-us/evalcenter/evaluate-windows-server-2025)

1. На Proxmox создайте эталонную ВМ **Q35 + OVMF (UEFI)** с системным диском **VirtIO SCSI** и сетевой картой **VirtIO**. Если на ноде есть NVMe, разместите на нём системный диск эталона. Установите Windows из подходящего ISO, драйверы VirtIO SCSI и NetKVM, обновления и QEMU Guest Agent. В локализованной Windows переименуйте встроенную учётную запись администратора (SID заканчивается на `-500`) в `Administrator`, сохранив её права. Проверьте загрузку эталонной ВМ с системного диска.
2. Установите [Cloudbase-Init x64](https://cloudbase.it/cloudbase-init/). В обоих файлах `cloudbase-init.conf` и `cloudbase-init-unattend.conf` проверьте источник ConfigDrive и имя пользователя. Проверьте, что целевая учётная запись включена и имеет административные права.

   ```ini
   [DEFAULT]
   username=Administrator
   inject_user_password=true
   metadata_services=cloudbaseinit.metadata.services.configdrive.ConfigDriveService
   ```

   В основном `cloudbase-init.conf` поместите установку пароля сразу после подготовки встроенной учётной записи. Пустой `groups` сохраняет её существующее членство по SID, поэтому имя локализованной группы не требуется.

   ```ini
   rename_admin_user=true
   groups=
   plugins=cloudbaseinit.plugins.windows.createuser.CreateUserPlugin,cloudbaseinit.plugins.common.setuserpassword.SetUserPasswordPlugin,cloudbaseinit.plugins.common.networkconfig.NetworkConfigPlugin,cloudbaseinit.plugins.windows.extendvolumes.ExtendVolumesPlugin
   ```

3. Выполните Sysprep с ответным файлом Cloudbase-Init, режимами **Generalize**, **OOBE** и **Shutdown**. Экспортируйте системный диск только после выключения. Эталон должен быть без пользовательских данных, сохранённых ключей и временных паролей. Не запускайте его повторно перед экспортом. [Подготовка шаблона Cloudbase-Init](https://cloudbase-init.readthedocs.io/en/latest/tutorial.html)

   Откройте командную строку от имени администратора и скопируйте ответный файл в каталог без пробелов в пути.

   ```bat
   copy "%ProgramFiles%\Cloudbase Solutions\Cloudbase-Init\conf\Unattend.xml" "%SystemRoot%\Temp\hv-unattend.xml"
   "%SystemRoot%\System32\Sysprep\Sysprep.exe" /oobe /generalize /shutdown /unattend:%SystemRoot%\Temp\hv-unattend.xml
   ```

4. На Linux-хосте подготовьте самостоятельный QCOW2 и имя файла для каталога. Для 2025 замените `edition` на `2025`. Команды требуют `qemu-img`, Python 3 и `sha256sum`.

   ```sh
   edition=2022
   input=/path/to/exported-system-disk
   qemu-img convert -O qcow2 "$input" windows-prepared.qcow2
   qemu-img check windows-prepared.qcow2
   gib=$(qemu-img info --output=json windows-prepared.qcow2 | python3 -c 'import json,sys; b=json.load(sys.stdin)["virtual-size"]; print((b + 1073741823)//1073741824)')
   digest=$(sha256sum windows-prepared.qcow2 | cut -c1-12)
   mv windows-prepared.qcow2 "homevlad-windows-server-${edition}-${gib}g-${digest}.qcow2"
   ```

5. Для другой зоны добавьте гипервизор в нужную **зону доступности** и разрешите его для заказов. На гипервизоре создайте файловое хранилище с типом **Import**. Загрузите туда именованный QCOW2 через Proxmox. В HomeVlad в «Образы ОС» → «Cloud-образы» выберите именно этот гипервизор, откройте нужную версию Windows, укажите хранилище и нажмите «Добавить в каталог». Для переноса загрузите подготовленный файл в новый Import и выберите его в панели. На каждой ноде, где нужно размещать такие ВМ, повторите публикацию или используйте доступное ей общее хранилище.
6. Для этой зоны настройте сетевой пул с DHCP и пул дисков с содержимым `images`. Хранилище Import держит исходник, системный диск новой ВМ создаётся в выбранном пуле дисков. Проверьте через тестовый заказ загрузку, появление сетевого адреса и вход в консоль под `Administrator`.

Импорт больших образов может занять до 10 минут. Для HTTP-заказов настройте тайм-ауты PHP-FPM и обратного прокси минимум на 660 секунд, если они завершают запрос раньше импорта.

В заказе Windows из готового образа установочный ISO и отдельный ISO драйверов не нужны. Панель генерирует ConfigDrive2 с временным паролем. Proxmox и служебный диск могут хранить этот пароль в открытом виде. Используйте одноразовое значение и смените его внутри Windows после первого входа. Имя заказа назначается ВМ в Proxmox. Чтобы поменять имя компьютера в госте, используйте настройки Windows или предусмотрите это в эталонном образе. При ручной установке переключитесь на ISO и выберите редакцию Windows. [Документация Proxmox по Cloud-Init](https://pve.proxmox.com/pve-docs/chapter-qm.html#qm_cloud_init)

## Боты Telegram

В разделе настроек администратора укажите разные токены для чат-бота и
бота поддержки. В кабинете привяжите Telegram и откройте личный чат с
каждым ботом через `/start`.

Запустите по одному CLI-процессу на токен. Возьмите [шаблон systemd](bots/homevlad-telegram@.service), замените `User` и `WorkingDirectory` для своего сервера, установите его в `/etc/systemd/system/` и выполните `systemctl daemon-reload`.

```sh
systemctl enable --now homevlad-telegram@chat homevlad-telegram@support
journalctl -u homevlad-telegram@chat -u homevlad-telegram@support -n 50
```

В Docker команды воркеров запускаются в контейнере Apache как два
долгоживущих процесса. Воркеры используют настройки БД приложения:

```sh
docker compose exec apache php bots/telegram_bot.php chat
docker compose exec apache php bots/telegram_bot.php support
```

Выполните эти команды в отдельных терминалах или под менеджером процессов.
Для режима опроса Telegram webhook должен быть отключён. После смены
токена перезапустите соответствующий воркер.

У чат-бота доступны меню, баланс, пополнение, список ВМ и переход к
поддержке. Бот поддержки показывает последние обращения и их статусы.
Создание обращения и переписка открываются в кабинете.

## Обновления через панель

В разделе «Обновления» администратор получает каталог выпусков из `updates/index.json` официального репозитория. Перед установкой проверяются SHA-256 и локальные изменения файлов. При конфликтах весь пакет останавливается для ручного слияния. Changelog доступен до запуска установки. Подготовка пакетов и восстановление описаны в [инструкции обновлятора](updates/README.md).

Пакеты обновляют файлы и транзакционно записывают версию в БД. Миграции схемы базы запускаются отдельно по инструкции выпуска. Во время установки панель временно отвечает HTTP 503. Если установка аварийно прервалась, сохранённый журнал блокирует работу до проверки и восстановления.

## Резервные копии и восстановление

В админке «Резервное копирование» доступны архивы файлов, базы данных и полные копии. Нужны расширение PHP ZipArchive, `proc_open` и клиент MariaDB/MySQL (`mariadb-dump`/`mysqldump`, `mariadb`/`mysql`). В Docker они уже включены. Дамп создаётся штатным клиентом с `--single-transaction`; согласованность снимка предполагает InnoDB и отсутствие изменений схемы во время копирования. Реквизиты клиента передаются через временный файл с правами 0600, который удаляется после команды.

Копии расписаний хранятся раздельно по их идентификаторам. При уменьшении лимита форма показывает количество старых копий, которые можно удалить сразу; удаление требует отдельной отметки. Запланированное создание копии применяет лимит только своего расписания. Ручные архивы имеют отдельный лимит 10; загруженные архивы и страховочные копии восстановления автоматически этим лимитом не удаляются.

Кнопка восстановления открывает предпросмотр архива: состав, компоненты, версия и исключения. Можно восстановить файлы, базу или оба компонента. Принимаются только доверенные архивы: восстановление файлов заменяет код приложения, импорт базы выполняет SQL из архива. Для запуска нужны актуальные права администратора, его пароль, CSRF-токен и текстовое подтверждение. Файлы, отсутствующие в архиве, сохраняются; таблицы БД заменяются полностью. Конфигурация, ключи и механизм аварийного восстановления сохраняются. Ключ `PROXMOX_NODE_KEY` нужно хранить отдельно: без подходящего ключа зашифрованные данные из старой базы не расшифруются.

Перед восстановлением остановите фоновые задания и внешние записи в БД. На время замены новые запросы панели блокируются. Страховочная копия исходных файлов и БД сохраняется в `backups/restore/<идентификатор>/`, автоматически не удаляется и занимает место на диске. При ошибке выполняется откат; при аварийном завершении остаётся журнал `backups/restore/recovery.json`, и панель остаётся закрытой. Для возврата к страховочной копии выполните из корня установки:

```sh
php cronjobs/restore_recovery.php rollback
```

Выполняйте команду от пользователя PHP/сайта. Не удаляйте журнал вручную, пока состояние файлов и базы не восстановлено. Восстановление архива сайта не восстанавливает внешние службы, конфигурацию Nginx/MyVestaCP, Docker-тома других сервисов или ключи вне веб-корня. Каталоги `backups`, `admin/backups` и логи должны быть закрыты веб-сервером.

В Docker архивы панели теперь сохраняются в отдельном bind-mount `./backups/archives`, страховочные копии — в `./backups/restore`. Перед первым пересозданием существующего контейнера с этой конфигурацией перенесите прежние архивы из него; прежний контейнер должен ещё существовать:

```sh
mkdir -p backups/archives
docker compose cp apache:/var/www/html/admin/backups/. ./backups/archives/
docker compose up -d --build
```

Если в старом контейнере каталога архивов нет, переносить нечего. Если копирование не удалось по другой причине, сначала сохраните архивы, затем пересоздавайте контейнер. Штатный веб-обновлятор обновляет файлы конфигурации в контейнере; host-файл Compose и пересоздание контейнеров администратор обновляет отдельно после переноса данных.

### Проверка шифрования узлов

Команда `php cronjobs/encrypt_node_passwords.php --check` показывает количество зашифрованных и старых записей и готовность ключа, не раскрывая реквизиты и не меняя БД. После резервного копирования и настройки постоянного ключа запустите команду без `--check` для транзакционного шифрования старых записей. Повторный запуск проверяет существующие шифротексты и не шифрует их повторно. Ключ должен быть доступен пользователям PHP и cron; на обычной установке это файл `.proxmox-node-key` на уровень выше веб-корня, на Docker — постоянный `PROXMOX_NODE_KEY` из окружения. Не меняйте его при пересоздании контейнера.

### Ограниченные API-токены Proxmox

В «Настройки Proxmox» → «Добавить ноду» укажите адрес API, порт, зону доступности, ID токена вида `billing@pve!homevlad` и его секрет. При редактировании поле секрета можно оставить пустым, чтобы сохранить текущее значение. Панель проверяет API, получает участников кластера и добавляет их в выбранную зону. Недоступные участники добавляются выключенными.

Создайте отдельного служебного пользователя и API-токен с включённым разделением прав. Назначьте права обоим по [политике ролей HomeVlad](includes/proxmox_token_policy.php). Секрет шифруется постоянным ключом установки. Подготовку токенов для старых подключений можно начать с команды `php cronjobs/prepare_proxmox_tokens.php --plan`. Режим `--prepare` требует действующих административных реквизитов и сохраняет проверенных кандидатов в закрытом каталоге. `--check` повторно проверяет кандидатов. Для Docker запускайте команды через `docker compose exec --user www-data apache`.

Проверьте из кабинета доступ к API и консоли QEMU и LXC. Подробнее о разделении прав — в [документации Proxmox](https://pve.proxmox.com/pve-docs/chapter-pveum.html).
